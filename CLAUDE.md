# Middagsplanlegger – regler for Claude Code

Fullstendig plan: `docs/plan.md`. Les den før du endrer noe stort. Språk i UI og dokumenter: norsk (bokmål).

## Prosjekt
Appens navn i UI, `<title>` og manifest er **«Husvett»** (eierens beslutning 2026-11-22). Interne navn (Middagsplanlegger, repo, Docker, `middag-*`-nøkler, filformat-id-er) er uendret og skal ikke byttes.
Landsdekkende norsk middagsplanlegger: ukeplan, én handlekurv, anslått pakningspris i én eller to butikker, kundeaviser. Fase 1 er en webapp (Vite + React + TypeScript). `npm run dev`, `npm test`, `npm run build`. Serveren bygges til én JavaScript-fil med esbuild (`npm run build:server`, `npm start`; `npm run server` = tsx, bare utvikling); Docker-imaget har bare `node`, den bygde serveren og `dist/`. `npm run smoke:server` og `npm run check:prod` tester produksjonsbygget. Importer i `server/` fra `src/` fungerer uten filendelse (esbuild), men ingen npm-pakke kan brukes av serveren uten at den bundles (bygget feiler ellers).

## Regler som ikke kan brytes
1. **Planmotoren (`src/engine/`) er ren og deterministisk.** Samme inndata og prisversjon gir samme kurv, sum og begrunnelse. Ingen `Date.now()`, tilfeldighet eller nettverk i motoren. Beløp i øre (heltall), mengder i g/ml/stk.
2. **Hver pris har kilde, geografisk omfang, dato og status** (ordinær, tilbud, estimat, ukjent). Historisk pris blir aldri automatisk dagens tilbud. Vis «anslått», aldri løfte om sluttpris.
3. **Ukjent pris vinner aldri** butikksammenligningen og gir svaret «Ufullstendig prisgrunnlag».
4. **Allergener:** appen garanterer aldri allergenfrihet. Uavklart allergenstatus godkjennes aldri som erstatning ved aktivt filter. Absolutte krav (kost, allergi) filtrerer; preferanser rangerer bare. Absolutte krav vinner over lås: `generatePlan` slipper ut låste retter som bryter allergi-, kost- eller råvarekrav (`lockedViolations`), og UI varsler og låser aldri slike retter. Tidsgrensen er unntatt.
5. **Demodata skal være merket som demodata.** Ikke presenter oppdiktede priser, butikker eller aviser som ekte. Ikke finn på leverandøravtaler eller dekningstall.
6. **Rettigheter:** bare avtalte eller lisensierte aviser, oppskrifter og bilder. Ikke hent kundeaviser selv. (Tjek-avtalen er brukerens opplysning, ikke avtaletekst vi har sett; se «Tilbudskilder» og `phase0/tjek-avtale.md`.)
7. **Personvern:** minst mulig persondata (postnummer, aldersgrupper, etiketter, porsjoner). Ingen presis posisjon eller barns navn. Ingen hemmeligheter i repoet; API-nøkler kun via miljøvariabler.
8. Importer og kjøpsbekreftelser skal tåle å mottas to ganger uten doble rader.

## Arbeidsmåte
- Nye regler i motoren krever test i `src/engine/planner.test.ts` (se regresjonslisten i planen).
- Ikke bygg funksjoner fra senere faser uten å bli bedt om det (KI = fase 3, egne apper = fase 3).
- Fase 0 er en port: uten dokumentert dekning bygger vi ikke videre som planlagt. Rapporter funn ærlig, også når dekningen er dårlig.
- Commit på brukerens utviklingsbranch. Ikke lag PR uten å bli bedt om det. Kjør `npm run check:git` før push: den feiler på usporede eller ignorerte filer under `src/`, `server/`, `scripts/`, `public/` (`.gitignore` ignorerer bare `/data/` i rota).

## Oppskrifter (`src/data/catalog.ts`, `docs/oppskrifter-tillatelser.md`)
- Hver oppskrift har `origin` (`RecipeOrigin`): `demo`, `egen` (egne ord og mengder, ikke kopiert) eller `lisensiert` (krever `credit`, https-`url`, `license` og et avsnitt for rettighetshaveren i `THIRD_PARTY.md`; testet med `originProblems`). Status `utkast` til testkokt, `godkjent` først når en redaktør har kontrollert, også allergener. `by` er rolle eller «KI-utkast (Claude)», aldri personnavn.
- Eieren (2026-11-22): oppskrifter fra nettet kan brukes når eieren har innhentet skriftlig tillatelse fra kilden. Før det kopieres ingenting (tekst, ingredienslister, bilder) og ingen nettsider skrapes. Import følger rutinen i `docs/oppskrifter-tillatelser.md`. Allergener settes alltid av oss ut fra varene, aldri fra kildens tekst.
- KI-utkast og aktive krav (eieren 2026-11-22, spørsmål 45): med allergi-, kost- eller råvarefilter er `egen` + `utkast` et absolutt brudd (`requirementViolation` → `'utkast'`, sist etter de konkrete bruddene; `isUnreviewedDraft`, `hasActiveRequirements`). De skjules derfor fra plan, bytte-, budsjett- og «fant ikke»-forslag, «Lag nå» og tilbudsretter, og `lockedViolations` slipper dem ut. Uten krav vises de som før. UI sier hvor mange som er skjult (`hiddenUnreviewed`, `unreviewedHiddenText`), og lover aldri allergenfrihet. `demo` omfattes ikke. `testkokt` slipper dem inn, så settes bare når en person også har kontrollert allergenene.
- Nye varer trenger produkt, demopris (regel 5) og næring (`scripts/build-nutrition.mjs`).
- Allergengjennomgang (`docs/allergen-gjennomgang.md`, `src/data/allergenSheet.ts`, `scripts/allergen-ark.ts`, `npm run allergen-ark`): ark for en person som kontrollerer allergener og kosttagger per oppskrift; alt kommer fra koden, skriptet retter ingenting og overskriver aldri utfylt arbeid (`--overstyr`). Kjør det på nytt når varer eller oppskrifter endres (testen sjekker at alle oppskrifter er med). `origin.status` settes til `godkjent` først når en person har fylt ut arket for retten.

## Tilbudskilder (`src/offers/`)
- Eksterne tilbud går gjennom `OfferSource` og normaliseres til øre og standardenheter. Planmotoren kjenner ikke kildene.
- Et tilbud gir bare rabatt når det er gyldig på **handledagen** og vare, pris, mengde og vilkår er kjent. Uavklart går til kontroll (`needsReview`).
- Tjek: skriftlig avtale finnes ifølge brukeren, men er fortrolig og ligger ikke i repoet. **Brukerens opplysning (2026-11-22), ikke avtaletekst vi har sett:** avtalen tillater **lagring av priser**, **bilder og avissider**, dekker **alle kjeder Tjek har**, og dekker at **AVVR AS bruker API-et i appen for andre brukere**. **Ikke kjent for oss, må bekreftes med Tjek:** kreditering, kallgrense, varighet og pris (også hvor lenge priser kan lagres og om logoer er med). Arbeidsregel til det er bekreftet: lagring bare på serveren i egen tabell uten persondata (aldri i husstandens synkdata, aldri synket); bilder og avissider bare fra Tjek-data, lastet fra Tjeks adresser (ikke lastet ned og lagret av oss), med «Kilde: Tjek» og dato; bare på appens egne sider, ingen videreformidling eller åpne nedlastinger (Tjeks offentlige vilkår § 8.2–8.6); kallbruk langt under § 8.5-taket. Kjedenes egne klausuler (Meny/SPAR/Joker punkt 16) er ikke klarert av oss. Se `THIRD_PARTY.md` og `phase0/RESULTS.md`.
- Tilbudslagring (`server/offers/`, `docs/synk.md` «Tilbud fra Tjek»): egen fil (`OFFER_DB`) og eget grensesnitt (`OfferStore`), aldri synk-lagringen og ingen persondata. Idempotent på (kilde, id); observasjonsdato er når Tjek viste prisen, aldri lesetiden. Periodisk henting med bakoff og kallbudsjett (`server/offers/collector.ts`), oppbevaring `OFFER_RETENTION_DAYS`. Klienten bruker `GET /api/offers/lagret` (husholdningstilbud i feltet `other`) og faller tilbake til live `/api/offers`; priser sett mer enn `MAX_PRICE_AGE_DAYS` før handledagen gir ikke hint. `TJEK_FETCH=0` i tester og røyktest.
- Bilder og kundeaviser fra Tjek (`server/offers/papers.ts`, `src/views/papers/TjekPapers.tsx`, `docs/synk.md` «Kundeaviser og bilder fra Tjek»): bare adresser hos Tjek, aldri nedlastede bildefiler; bare verter i `TJEK_IMAGE_HOSTS` (CSP `img-src` via `appCsp`, ellers `null`). Bilder lastes bare etter brukerens trykk (tilbudsdetalj, åpnet avis), med «Kilde: Tjek, hentet …». Formen på søk, kataloger og sider er prøvd mot ekte Tjek-svar 2026-11-22 (`phase0/tjek-formprøve.md`): `country_id` filtrerer ikke (vi filtrerer selv), `limit` høyst 100, ingen kategori, ingen rate limit-hoder, eneste bildevert `image-transformer-api.tjek.com`. Ingen kjedelogoer før Tjek bekrefter at logoer er med. «Aviser (demo)» er fortsatt demodata.
- Tilbudsrangering (`src/engine/deals.ts`): gyldige tilbud (på handledagen) med kjent pris, mengde og uten vilkårsord flytter valget av middager. Besparelsen regnes fra tilbudets egen førpris; tilbud uten førpris gir bare dekning. Tilbud endrer aldri butikksum eller kurv; allergi- og kostkrav slår alltid tilbud.
- Regelfil `src/data/offer-rules.json` (menneskekuratert, bare mønstre, aldri tilbud): `godkjent` kobler et mønster til en ingrediens, `avvist` stopper koblingen (med ingrediens) eller hele tilbudet (uten); `tillatt` er unntak fra utelukkelseslisten (f.eks. «soyasaus» trass i «saus») og gir bare forslag. Avvisning vinner alltid. Søkeordtreff uten regel er bare forslag. Redaktøren bruker Kundeaviser → Kontroll og eksporterer regelfilen; endringer sjekkes inn som vanlig kode.
- Kjeder (`src/engine/chains.ts`): `OfferHint.chain` er normalisert kjedenavn (`normalizeChain`, f.eks. «Coop Obs!» → «COOP OBS»). Bare tilbud fra kjeder i `Settings.offerChains` (valgfritt felt) teller i rangering og «Med kontrollerte tilbud» (`hintsForChains`). Ingen valgt kjede = ingen tilbud (`blocked: 'kjede'`), og appen ber brukeren velge. Tjek skiller ikke på utsalg: summen forutsetter at tilbudsvaren kjøpes hos den kjeden. Demobutikkene har ingen kjede.
- «Med kontrollerte tilbud» (`src/engine/offerTotal.ts`): egen sum ved siden av basissummen, bare regelgodkjente tilbud (`OfferHint.approved`), gyldige på handledagen, samme enhet; besparelse fra førpris, aldri over linjens pris. Fyller aldri ukjent pris, brukes ikke ved aktivt allergifilter, og endrer aldri basissum, butikksammenligning eller budsjettsvar.

## Beholdning og kjøp (`src/engine/inventory.ts`)
- Beholdning er en hendelseslogg (`kjøp`, `løs`, `angre`, `laget`, `telling`, `rest`). `applyEvent` er idempotent på hendelses-id; tilstanden avledes alltid av hele loggen sortert på (at, id), så ankomstrekkefølge spiller ingen rolle. Tid, id og enhets-id settes utenfor motoren (`stamp()` i `src/store.ts`).
- Forventet rest (`pantry.ts`) er aldri beholdning. Bare bekreftet hjemme (`telling`, bekreftet `rest`) og kjøpt-ikke-brukt trekkes fra behovet, via `Ctx.stock` = `deriveStock(log, { planWeek })`. Ukas egne kjøp, «laget» og rester holdes utenfor ukas egen kurv, og hendelser etter ukas første kjøp gjelder neste handel.
- Kjøp har linje-id (uke, butikk, vare, produkt): to voksne på samme linje gir ett kjøp. Ulikt antall fra ulike enheter er `konflikt`, teller ikke og må bekreftes med `løs`. En bekreftet rest er total mengde igjen etter ukas middager og erstatter ukas kjøp og forbruk av varen.
- En kjøpt pakke betyr ikke at retten er laget; forbruk registreres bare med `laget` (mengder fra `slotUses`).
- «Lag nå» (`src/engine/cookNow.ts`, `src/views/CookNowView.tsx`, fanen Matskap): forslag fra det som finnes hjemme (`deriveStock` uten `planWeek` + egne valg i `AppState.cookNow`, bare lokalt, aldri synket, endrer aldri loggen). Absolutte krav via `requirementViolation`; det som mangler prises med `basketForNeeds` (samme regler som kurven); ukjent pris rangeres aldri foran kjent ved ellers likt. «Legg manglende på handlelista» bruker `manuell`-linjer med prefiks `lagnå:<rett>|<vare>:` (én gang per rett og vare).
- «Bruk noe vi har hjemme» registreres som `hjemme` (linje-id per uke og vare, største mengde, angres med `angre`): legges til bekreftet hjemme og brukes opp av `laget`, holdes utenfor ukas egen kurv.
- Basisvarer (`src/engine/staples.ts`, `src/data/staples.ts`, `src/views/StaplesView.tsx`, Matskap → Basisvarer): varer husstanden alltid vil ha hjemme, delt i innstillingsdokumentet (`Settings.staples`, flettet per vare `basis:<id>`, `isValidStaples`), med minstemengde (bare varer som telles i matskapet) eller nivå (`nivå`-hendelser i `beholdning`). Under grensen i `deriveStock` (aldri telt = ukjent, ikke null) eller «snart tom»/«tom» gir forslag i handlelista; godkjenn/avvis = `manuell`/`manuell-fjern` med linje-id `basis:<uke>|<vare>`, aldri pris eller sum. Påvirker aldri kurv, sum, sammenligning, filtre eller rangeringen i «Lag nå». Egne navn: høyst 30 tegn, uten tall, logges aldri.
- Husholdningsvarer, utvidelse C (`src/engine/household.ts`, `src/data/household-rules.json`, `src/offers/household.ts`, `src/views/household/`, Kundeaviser → Husholdning, handlelista «Andre varer»): klassifisering av Tjek-overskrifter er ren og deterministisk med regelfil (søkeord med ordgrenser, utelukkelser, `sensitive` som aldri overstyres, `godkjent`/`avvist`/`tillatt`); bare `godkjent` godkjenner, alt annet er «trenger kontroll». Gruppene er generelle, uten bleier, medisin eller barneprodukter. Bare valgte kjeder, gyldig på handledagen, pris sett høyst 14 dager før. «Legg på lista» = `manuell` med linje-id `hus:<kilde>:<id>#<n>`, tekst = varenavn, merknad = kjede; pris og gyldighet synkes aldri, de slås opp i tilbudene (`householdTotal`). Egen sum «Andre varer»: aldri med i middagskurv, butikksammenligning, «Med kontrollerte tilbud» eller budsjett. Varegrupper i `Settings.householdGroups` (`isValidHouseholdGroups`). Fremheving bare nøktern (basisvare, lagt på lista før), aldri kjøpsoppfordring.
- Utboksen (`src/sync/queue.ts`) lagres lokalt og leveres til synk-serveren når enheten er med i en husstand. En mottaker må være idempotent på id.

## Utsolgt / fant ikke og planversjoner (`src/engine/substitution.ts`)
- Brukerens valg i butikken er en egen idempotent hendelseslogg (`erstatt`, `fant-ikke`, `angre-endring`), nøkkel (uke, butikk, vare, utsolgt produkt). Hvert valg har `prev` (valgene på linja enheten så); valg som ikke bygger på hverandre og sier ulikt er `konflikt` (ukjent pris, kan ikke markeres handlet) til en voksen velger. Eldre valg uten `prev` bygger på alle tidligere. Basiskurven endres aldri; `applyChanges` legger valgene oppå.
- Samme kurv overalt: `adjustedWeek` (motoren velger butikkene, valgene og den godkjente listen legges oppå, anbefalingen regnes på nytt). Ukeplan, handletur-kort, bytteforslag (`swapAdjust`), handleliste og «Med kontrollerte tilbud» bruker den; `ChangesNote` viser når valg er med.
- Erstatning: samme vare, gyldig pris i samme butikk, ikke utsolgt; ved aktivt allergifilter avvises allergentreff og uavklart status (sammensatte varer). Pakker regnes mot nettobehovet. «Fant ikke» uten videre valg gir ukjent pris (ufullstendig kurv); «hopp over»/«bruk hjemme» tar linja ut. Ingen av dem lager kjøp; linjer i «fant ikke» kan ikke markeres handlet, og en handlet linje må angres før den kan endres.
- Hver endring og godkjenning lagres som ny `PlanVersion` med årsak og `parents`; eldre versjoner endres aldri (opprinnelig anslag, også utløpt tilbud, står igjen). Versjonene synkes (strøm `planversjon`). En godkjent liste holder på produktene sine (`pinState`); gjeldende versjoner med ulike fastholdte produkter er en konflikt som løses med `chooseVersion`. Nye priser vises som avvik (`priceDrift`, brukerens valg regnes ikke som avvik) til brukeren velger «Bruk nye priser» eller «Behold godkjent liste».
- Godkjenning (`approvalVersion`) gir ny versjon bare når grunnlaget (middager, priser, valg, beholdning) er endret. Rettebytte ved «fant ikke» opphever godkjenningen. Tilstandsovergangene ligger i `src/listActions.ts` (brukes av UI og synk-tester).
- Planmotoren bruker aldri en pris med `validUntil` før handledagen (utløpt tilbud).
- Prisalder (`src/engine/prices.ts`, `resolvePrice`): bare observasjoner høyst `MAX_PRICE_AGE_DAYS` (14) dager eldre enn handledagen er kjent pris (alder i norsk dato: tid med sone regnes om med `osloDate` i `src/engine/oslo.ts`, fast regel uten klokke eller Intl, også på serveren); ellers brukes nyeste eldre observasjon som `estimat` med dato (aldri et gammelt tilbud uten gyldighet), og en gammel pris taper alltid mot en ny.

## Synk og husstand (`src/sync/`, `server/sync/`, `server/storage/`; se `docs/synk.md`)
- Offline først: skriv alltid lokalt (hendelse + utboks, eller dokumentfelt i `AppState`), aldri direkte til serveren. Appen skal virke uten server.
- Ingen siste-skriving-vinner. Delt data er enten idempotente hendelser (beholdning, handleliste, utsolgt / fant ikke, planversjoner) eller versjonerte dokumenter med tre-veis fletting og eksplisitt konflikt (plan, innstillinger). Ny delt data må passe inn i en av de to modellene.
- Avkrysning lagres per person (`by`); «fjern kryss» fjerner bare kryss enheten har sett. `by` er enhetens offentlige id; serveren avviser hendelser som utgir seg for et annet medlem.
- Identitet uten passord/e-post: enhetstoken (bare sha256 på serveren), engangsinvitasjon med utløp, bare eieren inviterer (`bare_eier`). Etiketter, ikke navn.
- Strenge feltlister: `cleanEvent` fjerner ukjente felt i `beholdning`, `liste` og `endring`; ny hendelsestype eller nytt felt må legges inn der (og i `versionOk` for `planversjon`).
- Gjenoppretting fra eldre kopi: serveren svarer `reset` (cursor etter `head` eller ukjent anker), eller dokumentets slekt (`revs`) viser at en sett versjon er borte (`lostDoc`); klienten sender sitt eget på nytt (`resetForRestore`). Cursor står alltid på siste hendelse (ankeret); dokumenter hentes med dokumentanker. Etter gjenoppretting flettes dokumenter tre-veis mot basen fra før (eldre kopi overses, nyere flettes, ukjent rekkefølge gir konflikt). `GET /healthz` til helsesjekk.
- Synkes aldri: postnummer, kostkrav og allergier (`avoid`, `avoidFoods`, `vegetarian`; mulige helseopplysninger), tilbud fra Tjek (heller ikke pris eller overskrift på «Andre varer»-linjer). Serveren avviser ukjente felt.
- Alle endepunkter: autentisering avgrenset til husstanden, ratebegrensning, størrelses- og lengdegrenser, norske feilkoder. Ny lagring implementerer `SyncStorage` (PostgreSQL senere).
- Endringer i synk krever test i `server/sync/api.test.ts` eller `src/sync/engine.test.ts`.
- Personvern (`docs/synk.md`, «Personvern i appen» og «Oppbevaringstid»): «Last ned mine data» (`src/sync/export.ts` + `GET /api/household/export`) tar aldri med token, hash, kode eller interne id-er; nye lagrede felt må med i eksporten. Arket «Personvern» (`src/views/PrivacySheet.tsx`) er UTKAST og skal ikke love mer enn koden gjør. `server/retention.ts` sletter husstander uten autentisert aktivitet i `SYNC_RETENTION_DAYS` (standard 730 etter eierens valg 2026-11-22, 0 = av, ugyldig verdi gir 730 med advarsel; injisert klokke). Innloggingen (enhetstoken) utløper etter `SYNC_TOKEN_IDLE_DAYS` (standard 730, 0 = aldri). «Eier godkjenner nye medlemmer» er utsatt.
- Introduksjon og tilbakemelding (pilot; `src/views/Intro.tsx`, `src/views/HelpCard.tsx`, `src/views/feedback.ts`): introduksjonen vises til den lukkes på enheten (`introSeen` i `AppState`, `showIntro`/`closeIntro`; lokal, synkes aldri, med i eksporten under enheten og forklart), er ikke modal og åpnes igjen fra Husstand → Hjelp. «Gi tilbakemelding» er mailto til `CONTACT_EMAIL` (ikke bekreftet i drift, byttes der) med mal og uten noe fra enheten; adressen står også som tekst med kopier-knapp. Ingen svarfrist. Tekstene lover ikke mer enn koden (test `src/acceptance/introduksjon-ui.test.tsx`).
- Sikkerhet (`docs/sikkerhet.md`): nye endepunkter og lagring må holde kvotene (`kvote_full`), aldri logge token, kode, etikett eller feilmelding, og gi samme 401/404 uansett om noe finnes. Nye hendelsesstrømmer har `at` (klippes fram i tid) og streng feltliste. CSP i `server/app.ts` er streng (ingen inline-skript, Trusted Types; eneste tredjepart er bildeverter fra `TJEK_IMAGE_HOSTS` i `img-src`); sjekk med `npm run check:csp`. Negative tester i `server/sync/security.test.ts`.
